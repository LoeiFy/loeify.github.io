让 Agent 在 CI 里值班：Sentry 错误自动分类与修复

一套在 CI 中无人值守运行的 Sentry 错误处理方案：Agent 每周拉取线上错误、判断是否为代码问题，能修则提 PR，不能修则输出诊断，最后汇总为一个 GitHub Issue 并发送群通知。本文覆盖上报层设计、执行流程、设计取舍与方案边界，文末附可复用的提示词骨架（已脱敏）

一、背景与目标

前端上线后，Sentry 里的错误会持续累积。传统做法是有人定期打开后台逐条 triage——成本高、易拖延，而且大量"非代码问题"（资源加载失败、网络抖动、请求取消）混在真正的缺陷里，人工筛选纯属浪费。

目标是把这条链路自动化，四条原则：

  1. 每周自动汇总：拉取最近 7 天的 production 错误，生成结构化周报；

  2. 能修则修：定位明确、改动可控的问题，自动提交最小修复 PR；

  3. PR 不合并：只创建，人工 review 是终点；

  4. 通知闭环：无论结果如何都发群通知，"本周必有回音"。

方案有两半：CI 里的流水线（拉取、分类、修复）和页面里的自建上报层（src/utils/sentry）。错误先被上报得干净，Agent 才能挑得准——两者是配套关系。

定时触发（每周）

  → 2. 分类：代码问题 / 非代码问题

输入只有两个凭据：SENTRY_TOKEN（只读，拉 issue 与堆栈）、GITHUB_TOKEN（克隆、推分支、建 PR/Issue）。 输出三类：修复 PR、汇总 Issue、飞书通知。三者联动：PR 描述标注 Sentry issue ID，汇总 Issue 汇集所有条目与 PR 链接，飞书通知带汇总 Issue 的真实 URL。

三、上报层：流水线的地基

项目没有裸用 @sentry/browser，而是在 src/utils/sentry 封装了约 10 个模块，解决三件事：怎么收、哪些不报、怎么分级打标。

模块 职责
index.ts init 入口：接管全局处理器、串联过滤链、补报初始化前缓存的事件
config.ts ignoreErrors 忽略规则、API 忽略状态码、whiteScreenChecker
error.ts error 事件：资源错误 / JS 错误分流 + 白屏感知分级
unhandledrejection.ts Promise rejection 处理，统一打 unhandledError 标签
api.ts HTTP 失败请求：apiError 标签，按状态码分级
filter.ts 同页面内按 traceId + 错误内容去重
context.ts captureWithContext：带上下文块的手动上报
biz.ts captureBizException：业务兜底错误上报
freeze.ts Worker 心跳检测 UI Freeze，直接构造 Envelope 上报

1. 接管全局处理器，统一收口

init 里过滤掉 Sentry 内置的 GlobalHandlers，改用 window.sentry_captureError / sentry_captureUnhandled 自行捕获。好处是所有错误入 Sentry 前都经过同一套分级和打标，顺带解决 SDK 初始化前丢错误的问题——早期事件先缓存在 window.sentry_* 数组，init 后统一补报。

2. errorType 标签体系：为流水线而设计

errorType 来源 附加标签
error JS 运行时错误 errorName
unhandledError 未处理 Promise rejection errorName
apiError HTTP 4xx/5xx status_code
resourceError 图片等资源加载失败 tagName、src
bizError 业务兜底错误 apiPath

因此查询条件 errorType:[unhandledError,error] 天然排除资源、API 和业务错误。这不是巧合：打标在上游就为下游分流做好了准备，分类步骤里的"非代码问题"有相当一部分在这里已被挡掉或降级。

3. 白屏感知分级

同一个 JS 错误，白屏与非白屏下严重级别完全不同：whiteScreenChecker()（检查 #root 是否为空）为真时，动态导入失败降为 warning（多为发布切换期瞬态问题），其余标 fatal；非白屏时按错误性质给 error / warning。资源错误（event.error === undefined）统一降级并附 tagName / src，不进错误主线。

4. 发送前的过滤链

beforeSend 串起三层闸门：

  • config.ignoreErrors：已知噪音直接不报——ResizeObserver loop、浏览器插件（extension://）、Script error、请求取消（CanceledError / ECONNABORTED / timeout of xms exceeded）；

  • api.ts：识别 HTTP 失败（auto.http.client.xhr/fetch），401 丢弃，5xx 保持 error，4xx 降为 warning；

  • filter.ts：同页面内 traceId + 错误内容 + URL 完全一致只报一次，防刷屏。

噪音在客户端就被拦掉，服务端拉到的基本都是"值得看"的事件，错误量因此可控。

5. captureWithContext：埋点的标准入口

真实签名与直觉不同：第二个参数不是扁平对象，而是"上下文块名 → 数据"的映射。

export default function captureWithContext(
  error: unknown,
  contexts: Record<string, Record<string, unknown>>
) {
  Sentry.withScope((scope) => {
    Object.entries(contexts).forEach(([name, data]) => scope.setContext(name, data));
    scope.setLevel("error");
    Sentry.captureException(error);
  });
}

所以在 Sentry 后台，各块是独立 context，比扁平 extras 更可读、更好检索。另一个封装 captureBizException 只在接口返回兜底 code（-1）时上报，避免业务异常码刷爆列表。

6. Worker 心跳：主线程卡死也能上报

普通上报有盲区：主线程 freeze 时 SDK 自身也发不出事件。freeze.ts 启动 Blob Worker，与主线程每 5 秒互发心跳；超时即判定 dead，由 Worker 用 fetch + keepalive: true 直接构造 UI Freeze 事件（fatal），附内存占用、页面 URL 与最后活跃时间。它不进入流水线查询，但在 Sentry 后台是独立的 fatal 信号。

四、流水线执行详解

1. 拉取本周错误 

1
2
3
4
 
curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<org>/issues/?project=<id>\
&environment=production&query=errorType%3A%5BunhandledError%2Cerror%5D\
&statsPeriod=7d&sort=recommended&limit=100"

关注字段：id（关联堆栈与 PR）、metadata.value（分类核心依据）、permalink（写入 Issue 与 PR）、count / level（影响面与优先级）。

异常路径先于主流程定义：接口非 200 → 不建任何 GitHub 资源，直接发红色卡片（含状态码与错误信息）；返回空数组 → 不发 PR、不建 Issue，发蓝色卡片"本周无需要处理的错误"。

2. 判断是否为代码问题

标准刻意机械化，避免 Agent 自由发挥。依据只有一条：能否从 metadata.value 提取出具体异常类型或代码行为描述。

  • 非代码问题：网络 / 资源加载失败、无有效堆栈。典型如 Object captured as exception with keys: ...、Network Error、Unable to preload CSS for ...、Importing a module script failed.；
  • 代码问题：包含明确异常类型和可定位描述，如 TypeError: Cannot read properties of null (reading 'someField')。

非代码问题不丢弃，作为条目记入汇总 Issue，附可能原因与排查建议。资源类错误根因通常在发布流程或 CDN 缓存，不属代码修复范畴。

3. 合并重复 issue

同一缺陷常产生多个 issue（行号、调用路径、release 不同）。满足任一即视为同根因：错误文本高度相似且指向同一对象；堆栈文件与函数相同、仅行号/路径不同；同一模块相近位置；信息与位置相同、仅 release / environment 不同。

合并规则：同根因只建一个 PR（描述列全部 issue ID 与链接）；汇总中并为一条并注明"对应 N 个 Sentry issue"；不确定时不合并。

保守是有意为之：宁可多修一个，不要错并一个——错误合并会让一个 PR 同时改两处无关代码，违背最小单点修复。

4. 分析与修复

逐个问题拉取最新事件堆栈：

1
2
3
 
curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<org>/issues/<issue-id>/\
events/latest/?full=true&environment=production"

先过修改上限硬闸门，再选模式。

硬闸门（任一命中即转报告模式）：涉及文件 > 2；跨 2 个以上不相关模块；候选修改位置 > 5 处；根因涉及业务逻辑（而非取值路径、空值保护这类机械错误）。同时限定搜索范围：只查堆栈中出现过的项目内文件与函数，忽略框架帧，调用链最多追一层——防止 Agent 在代码库里"漫游"。

模式二选一：根因能否从代码本身确定？

  • 能确定（取值路径写错、缺空值判断）→ 直接修复，不加埋点。例如路由 state 导致的 crash，从代码即可确认根因：

if (!msg?.targetId) {

为什么缺一不可？ 只防护不上报，问题会从"崩溃"退化为"静默失效"——用户没反应，Sentry 里也再无记录，等于亲手掐断线索。埋点要一次带够定位所需数据，避免复现后再补埋点、再等一周。

三个配套细节：调用封装前必须先读真实签名，按直觉写会静默丢上下文；埋点抛描述性 Error 而非裸对象（去重依赖错误文本，打标依赖异常类型）；PR 描述注明是直接修复还是治标（治标须写明根因未确认、已补上报、可疑假设标"待验证"）。

报告模式（无写操作，输出结构化诊断）：技术影响级别（白屏 / 操作失效 / 局部报错）、业务影响级别（推测 + 依据，待人工确认）、根因假设 + 依据、建议下一步。让"没修"的条目依然有信息量。

5. 创建汇总 Issue

整个任务唯一创建的 Issue，标题 Sentry 周报修复总结 - {YYYY-MM-DD}，逐条列出：issue 名称 + Sentry 链接、分类、代码问题的"已解决（方案 + PR 链接）"或"未解决（原因 + 建议）"、非代码问题的可能原因 + 建议；合并项只列一条并注明 N 个关联 issue。

6. 飞书群通知

情况 卡片颜色 内容
A 正常完成 有未解决 orange / 全解决 green 处理统计 + "查看汇总 Issue"按钮
B 接口失败 red 状态码 + 错误信息
C 无 issue blue "本周未返回需要处理的错误"

两条注意：Issue URL 必须取自创建 Issue 的 API 返回，不可拼造；飞书发送失败不影响已完成的 GitHub 操作，无需回滚。

五、关键设计取舍

决策 理由
自建上报层打 errorType 标签 原生 Sentry 只有裸事件，各类错误混在一起。标签体系是两个系统之间的契约，让查询精确、分类有底
判断标准全部机械化 看 metadata.value、看四条可枚举的去重规则、看根因能否静态确定——可机械执行就没有"发挥失误"的空间。凡需主观判断（如业务影响）一律标"推测 + 依据，待人工确认"
修改上限硬闸门 自动修复的价值集中在"单点、机械、可静态验证"的错误（典型是空值保护）。改动面一大，静态置信度骤降，review 成本反超收益，宁可漏修不可错修
防护 + 埋点成对 最易被忽略也最关键：只防护会让问题从监控里消失而依然存在。强制成对保证治标不丢线索
单 issue 单分支单 PR 混合修复一旦某处有问题会拖累整体合并，也无法单独 revert
PR 永不自动合并 自动合并省几分钟，赌的是线上稳定性。涉及公共函数 / 导出方法时在描述里标注"可能影响其他调用方，需人工确认"
异常路径先定义 无人值守系统最怕的不是失败，而是失败后行为未定义

六、收益与代价

收益：错误处理周期从"数周"压缩到"一周内"（fatal 可单独提高频率）；triage 这类低价值劳动完全自动化；每个修复有 Sentry issue ↔ PR ↔ 汇总 Issue 的完整引用链；每周必有回音，"沉默"本身成为需要警惕的信号；不合并、单点提交、硬闸门、报告模式兜底，每步都有刹车。

代价与边界：

  1. 单点修复 ≠ 根治：反复出现、影响面大的问题往往卡在业务逻辑或架构层，恰是 Agent 修不了只能报告的部分；

  2. 治标会累积：埋点上报后若无人跟进验证，防护代码长期留存，埋点变成新噪音；

  3. 启发式会误判：文本相似度、堆栈位置规则有误差，代价是可能产生重复 PR；

  4. 静态置信度有天花板：Agent 跑不了真实回归测试，"可选链不会破坏逻辑"只能靠静态推理 + 人工 review 兜底；构建复杂、宏多、类型体操重的项目误改风险更高；

  5. 业务语义理解有限：报告里的"根因假设""业务影响"本质是推测，直接采信会引入新风险；

  6. 规则有维护成本：过松放大风险，过严让 Agent 长期"只报告"，自动化名存实亡；

  7. 上报层自身有盲区：接管 GlobalHandlers 需自行跟进 SDK 升级；过滤过激会挡住真错误（如发布窗口外出现的动态导入失败可能被低估）；filter.ts 依赖内存数组，刷新后计数清零；

  8. 权限心智负担：给 CI Agent 仓库写权限本身就需要谨慎评估。

落地注意：凭据最小权限（Sentry 只读、GitHub 限定目标 repo）；项目规范若要求"实施前必须与用户确认"，无人值守场景需显式豁免，否则 Agent 会卡死；environment=production 与 release:latest 要按实际调整，防止 dev/test 混入；上报层过滤规则应随噪音演进，新业务上线后先考虑在上游过滤而非在流水线加特判；若连续几周都是"非代码问题 8 个"，该回头查发布流程或上报策略；标题日期用执行当天，统计范围固定为执行时刻往前 7 天。

七、结语

方案的本质是把自动化用在置信度最高的环节：拉取、分类、去重、通知是确定性工作，全自动；单点机械修复是高置信工作，自动化 + 人审；业务逻辑与架构问题是低置信工作，只做结构化诊断。三条线各归其位，才敢无人值守。

建议先以"只报告不修复"跑两三周，观察分类准确率与报告质量，再逐步打开修复模式——这也是我们实际走过的路径。

你是一个前端工程师，在 CI 中自主执行 Sentry 错误修复任务，无人实时参与。
从 Sentry 获取最近一周的错误，判断是否为代码问题，能修则提 PR，
最后创建汇总 GitHub Issue 并发送飞书群通知。
异常或无数据情况下只发飞书通知，不创建 GitHub Issue。

# 基本信息
- SENTRY_TOKEN：获取 Sentry 最近 issues
- GITHUB_TOKEN：GitHub CLI 操作 repo
- GitHub repo：<your-org>/<your-repo>

# 全局规则
- 搜索：只查堆栈中出现的项目内文件和函数，忽略框架帧；每次最多 5 个结果；
  调用链最多追踪一层；禁止通用关键词开放式搜索。
- 修改上限：动手前先声明涉及文件。若文件 > 2、跨 2 个以上不相关模块、
  候选位置 > 5、或根因涉及业务逻辑，不改代码，直接报告。
- 修复模式：每个可修复问题独立分支，最小单点修复，发起 PR，
  PR 标题或描述注明对应的 Sentry issue ID。
- PR 不自动合并，等待人工 review。
- 回归风险：PR 描述注明是否涉及公共函数或导出方法；若是，
  标注"可能影响其他调用方，需人工确认"。
- 报告模式：不调用写操作，输出结构化诊断（issue 链接、根因、涉及文件行号、
  建议方案、未自动修复的原因），最终写入汇总 issue。
- 禁止：顺手修无关问题、混合多个修复、无法定位时猜测性修改。

# 前置：项目上报层（可选，有则利用）
- 查询条件应与上报层的 errorType 标签对齐（error/unhandledError/apiError/
  resourceError/bizError）。
- 埋点必须使用其封装的真实签名（如 captureWithContext(error, contexts)，
  contexts 为"块名 → 数据"映射），不得假设 API 形态。

# 操作流程
## 1. 获取本周 Sentry 错误
curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<your-org>/issues/?project=<project-id>\
&environment=production&query=errorType%3A%5BunhandledError%2Cerror%5D\
&statsPeriod=7d&sort=recommended&limit=100"
- 接口失败（非 200）：不建 issue，跳到步骤 6 发红色卡片，说明状态码和错误信息。
- 空数据：不发 PR、不建 issue，跳到步骤 6 发蓝色卡片。

## 2. 判断是否为代码问题
- 非代码问题（跳过修复，仅记录）：网络/资源加载失败或无有效堆栈，
  如 "Object captured as exception with keys: ..."、"Network Error"、
  "Unable to preload CSS for ..."。
- 代码问题：包含明确异常类型和可定位代码位置。
- 依据：能否从 metadata.value 提取具体异常类型或代码行为描述。

## 3. 合并重复 issue
- 同一根因（满足任一）：文本高度相似且指向同一对象；堆栈文件与函数相同
  仅行号/路径不同；同一模块相近位置；信息/位置相同仅 release 或 environment 不同。
- 同一根因只建一个 PR，描述列出所有 issue ID 和链接；汇总中合并为一条并注明
  "对应 N 个 Sentry issue"；不确定时不合并。

## 4. 分析并尝试修复
curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<your-org>/issues/<issue-id>/\
events/latest/?full=true&environment=production"
- 堆栈获取失败：归入报告模式，注明"无法获取有效堆栈"。

### 修复模式
- 根因代码内可解 → 直接修复，不加埋点。
- 根因在运行时/数据/接口，静态无法确认 → 防护 + 埋点成对：
  1) 防护：最小改动防崩溃（可选链、空值判断）；
  2) 埋点：调用 Sentry.captureWithContext(error, contexts)，contexts 为
     "上下文块名 → 数据"映射（非扁平对象），至少含出错对象全量、缺失字段、
     触发上下文（页面/操作/状态）、关联请求（traceId），一次带够；
     error 须为描述性 Error 实例；使用前须查看封装真实签名。
  禁止只加防护不加上报。
- PR 描述注明直接修复还是治标；治标须说明根因未确认、已补上报、
  可疑假设标"待验证"。

### 报告模式
不建 PR、不发 issue，只记录诊断：技术影响级别（白屏/操作失效/局部报错）、
业务影响级别（推测+依据，待人工确认）、根因假设+依据、建议下一步。

## 5. 创建汇总 GitHub Issue（本次唯一创建的 issue）
- 标题：Sentry 周报修复总结 - {YYYY-MM-DD}
- 内容逐条列出（合并项只列一条并附全部链接）：issue 名称+链接、分类、
  已解决方案+PR 链接 / 未解决原因+建议、非代码问题的可能原因+建议。

## 6. 发送飞书群通知
- 情况 A（正常完成）：orange 或 green 卡片，统计文案 + "查看汇总 Issue"按钮，
  按钮 URL 取自步骤 5 的 API 返回，不自行编造。
- 情况 B（接口失败）：red 卡片，说明状态码和错误信息。
- 情况 C（无 issue）：blue 卡片。
- Webhook：<your-lark-webhook-url>
- 飞书发送失败不影响已完成的 GitHub 操作，无需回滚。
