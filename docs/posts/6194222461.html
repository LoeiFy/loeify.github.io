让 AI 每周替我们翻一遍 Sentry

上线之后 Sentry 里的错误一直在涨，真正去看的人却越来越少。

我们之前是每周排一个人翻后台，一条条点开判断是不是代码问题。这件事的麻烦不在于占多少工时，而在于它总能往后拖；而且列表里大量条目根本不是代码问题——图片 404、网络抖动、用户主动取消的请求，和真正的错误崩溃混在一起，人工筛一遍大半是在做无用功。

后来我们把这段流程交给了 CI 里的一个 Agent。它每周跑一次，拉最近 7 天的 production 错误，能定位的直接提 PR，定位不了的写诊断，无论结果如何最后都在飞书群里发一条消息。

约束很明确：

  • 只拉 production，只覆盖最近 7 天；
  • PR 只创建不合并，人工 review 是终点；
  • 每周必须有一条群消息，内容可以是"本周没有需要处理的错误"。

方案由两块组成：CI 里的流水线，以及页面里的自建上报层（src/utils/sentry）。顺序是先有干净的上报，Agent 才挑得准，所以下面先讲上报层，再讲流水线。

每周定时触发
  → 拉取 Sentry 近 7 天 production 错误（errorType:[unhandledError,error]）
  → 分类：代码问题 / 非代码问题
  → 去重：同一根因合并成一个修复单元
  → 逐条处理：能修的分支 + PR，不能修的只留诊断
  → 创建当周唯一一个汇总 GitHub Issue
  → 飞书群卡片通知，附汇总 Issue 链接

输入只有两个凭据：SENTRY_TOKEN（只读，用来查 issue 和堆栈）和 GITHUB_TOKEN（克隆、推分支、建 PR 和 Issue）。输出三类：修复 PR、汇总 Issue、群通知。三者之间有引用关系——PR 描述里带 Sentry issue ID，汇总 Issue 列出所有条目和对应 PR，群消息里的链接取自创建 Issue 那一步的返回值。

二、上报层

项目没有裸用 @sentry/browser，而是在 src/utils/sentry 下包了十个左右模块。要解决的问题就三个：错误怎么收、哪些不报、怎么分级打标。

模块 职责
index.ts init 入口，接管全局处理器、串起过滤链、补报初始化前缓存的事件
config.ts ignoreErrors 规则、API 忽略状态码、whiteScreenChecker
error.ts error 事件，资源错误与 JS 错误分流，白屏感知分级
unhandledrejection.ts Promise rejection，统一打 unhandledError
api.ts HTTP 失败请求，打 apiError，按状态码分级
filter.ts 同页面内按 traceId + 错误内容去重
context.ts captureWithContext，带上下文块的手动上报
biz.ts captureBizException，业务兜底错误上报
freeze.ts Worker 心跳检测 UI Freeze，直接构造 Envelope 上报

接管全局处理器

init 里把 Sentry 内置的 GlobalHandlers 从 integrations 中去掉，改用 window.sentry_captureError 和 sentry_captureUnhandled 自己接管。这样所有错误在进 Sentry 之前都会走同一套分级和打标逻辑。顺带解决了一个老问题：SDK 初始化之前发生的错误会丢，现在先缓存在 window.sentry_* 数组里，init 之后统一补报。

errorType 标签

errorType 来源 附加标签
error JS 运行时错误 errorName
unhandledError 未处理的 Promise rejection errorName
apiError HTTP 4xx/5xx status_code
resourceError 图片等资源加载失败 tagName、src
bizError 业务兜底错误 apiPath

流水线的查询条件写的是 errorType:[unhandledError,error]，资源、API、业务错误因此天然被排除在外。我们当初做这套标签只是为了在后台里区分错误来源，后来发现它刚好成了两个系统的接口约定：标签在上报时就打好了，查询端才能写得这么简单，分类那一步的负担也轻了不少。

白屏分级

同一个 JS 错误，白屏和非白屏下的严重程度完全不同。whiteScreenChecker() 检查 #root 是否为空：

  • 白屏时，动态导入失败降到 warning（大多是发布切换时的瞬态问题），其余标 fatal；
  • 非白屏时，按错误性质给 error 或 warning；
  • 资源错误（event.error === undefined）统一降级，附 tagName 和 src，不进错误主线。

beforeSend 里的三层过滤

  • config.ignoreErrors：已知噪音直接不报。ResizeObserver loop、浏览器插件（extension://）、Script error、请求取消（CanceledError / ECONNABORTED / timeout of xms exceeded）都在这个列表里。
  • api.ts：识别 HTTP 失败（auto.http.client.xhr/fetch）。401 丢掉，5xx 保持 error，4xx 降为 warning。
  • filter.ts：同页面内 traceId、错误内容、URL 三者完全一致只报一次，防止同一错误把列表刷屏。

噪音在客户端就拦掉了，服务端拉到的事件基本都是值得看的，量也可控。

captureWithContext 的签名

这个封装的第二个参数不是扁平对象，而是"上下文块名 → 数据"的映射，跟我们第一版按直觉写的不一样：

export default function captureWithContext(
  error: unknown,
  contexts: Record<string, Record<string, unknown>>
) {
  Sentry.withScope((scope) => {
    Object.entries(contexts).forEach(([name, data]) => scope.setContext(name, data));
    scope.setLevel("error");
    Sentry.captureException(error);
  });
}

结果是 Sentry 后台里每块数据是独立的 context，比塞进 extras 可读，也方便按字段检索。另一个封装 captureBizException 只在接口返回兜底 code（-1）时上报，避免业务异常码占满列表。

Worker 心跳

普通上报有个盲区：主线程卡死的时候，SDK 自己也发不出事件。freeze.ts 起了一个 Blob Worker，和主线程每 5 秒互发一次心跳，超时就判定 dead，由 Worker 用 fetch 加 keepalive: true 直接构造 UI Freeze 事件（fatal），带上内存占用、页面 URL 和最后活跃时间。这类事件不进流水线查询，但在后台是一个独立的信号。

三、流水线

拉取

curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<org>/issues/?project=<id>\
&environment=production&query=errorType%3A%5BunhandledError%2Cerror%5D\
&statsPeriod=7d&sort=recommended&limit=100"

要用的字段不多：id（关联堆栈和 PR）、metadata.value（分类的核心依据）、permalink（写进 Issue 和 PR）、count 和 level（影响面与优先级）。

异常路径先于主流程定好。接口返回非 200，不建任何 GitHub 资源，直接发一张红卡片，写明状态码和错误信息；返回空数组，不发 PR 也不建 Issue，发蓝卡片说本周没有需要处理的错误。无人值守的系统里，最怕的不是失败，而是失败之后行为没有定义。

判断是不是代码问题

标准我们刻意写得机械，不让 Agent 自由发挥。依据只有一条：能不能从 metadata.value 里提取出具体异常类型或代码行为描述。

  • 非代码问题：网络或资源加载失败、没有有效堆栈。典型文本是 Object captured as exception with keys: ...、Network Error、Unable to preload CSS for ...、Importing a module script failed.。
  • 代码问题：有明确异常类型，描述能定位到代码位置。比如 TypeError: Cannot read properties of null (reading 'someField')。

非代码问题不丢，作为条目记进汇总 Issue，附上可能原因和排查建议。资源类错误的根因多半在发布流程或 CDN 缓存，本来也不该由代码修复来管。

合并重复 issue

同一个缺陷经常散成多个 issue，区别只在行号、调用路径或 release。满足任一条就算同根因：

  • 错误文本高度相似，且指向同一个对象；
  • 堆栈文件与函数相同，只有行号或路径不同；
  • 同一个模块的相近位置；
  • 信息和位置都相同，只有 release 或 environment 不同。

合并之后，同根因只建一个 PR，描述里列全部 issue ID 和链接；汇总里并成一条，注明"对应 N 个 Sentry issue"。拿不准的时候不合并。

宁可多修一个，也不错并一个。合错了的后果是一个 PR 同时改两处无关代码，既违背最小单点修复，也没法单独回滚。

分析与修复

逐条拉最新事件的堆栈：

1
2
3
 
curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<org>/issues/<issue-id>\
/events/latest/?full=true&environment=production"

动手之前先过修改上限，命中任一条就转报告模式：涉及文件超过 2 个；跨 2 个以上不相关模块；候选修改位置超过 5 处；根因涉及业务逻辑，而不是取值路径、空值保护这类机械错误。

搜索范围也一并限死：只查堆栈里出现过的项目内文件和函数，忽略框架帧，调用链最多追一层。不加这条，Agent 很容易在代码库里到处逛，最后交上来一个看不出因果的 diff。

接下来按根因能不能从代码本身确定来分两种模式。

能确定的时候直接修，不额外加埋点。比如路由 state 导致的 crash，看代码就能确认：

只防护不上报的坏处我们吃过一次：崩溃变成了静默失效，用户点了没反应，Sentry 里也没有任何记录，线索是自己掐断的。所以这两件事强制配对。埋点一次要把定位需要的数据带够，否则复现之后再补埋点，又得等一周。

三个容易踩的细节：调封装之前先读真实签名，按直觉写会静默丢上下文；埋点抛描述性的 Error 实例而不是裸对象，去重依赖错误文本，打标依赖异常类型；PR 描述写清是直接修复还是治标，治标的要注明根因未确认、已补上报、可疑假设标"待验证"。

报告模式不调用任何写操作，输出固定几项：技术影响级别（白屏 / 操作失效 / 局部报错）、业务影响级别（推测加依据，待人工确认）、根因假设和依据、建议的下一步。这样没修的条目也有信息量，不至于变成一句"无法自动修复"。

汇总 Issue

整个任务只创建这一个 Issue，标题是 Sentry 周报修复总结 - {YYYY-MM-DD}。逐条列：issue 名称和 Sentry 链接、分类、代码问题的"已解决（方案 + PR 链接）"或"未解决（原因 + 建议）"、非代码问题的可能原因和建议。合并过的条目只列一条，注明关联了几个 issue。

群通知

情况 卡片颜色 内容
正常完成 有未解决 orange，全解决 green 处理统计 + "查看汇总 Issue"按钮
接口失败 red 状态码 + 错误信息
无 issue blue "本周未返回需要处理的错误"

两个细节：按钮的 URL 必须取自创建 Issue 的接口返回，不能自己拼；飞书发送失败不影响已经完成的 GitHub 操作，不需要回滚。

四、几个设计取舍

决策 理由
自建上报层打 errorType 标签 原生 Sentry 只有裸事件，各类错误混在一起。有了标签，查询精确，分类也有据可依
判断标准全部机械化 看 metadata.value，看四条可枚举的去重规则，看根因能否静态确定。能机械执行的地方就没有发挥失误的空间；凡是要主观判断的（比如业务影响）一律写"推测 + 依据，待人工确认"
修改上限的硬闸门 自动修复的价值集中在单点、机械、可静态验证的错误，典型就是空值保护。改动面一大，静态置信度掉得很快，review 成本反超收益，宁可漏修不可错修
防护与埋点成对 只防护会让问题从监控里消失但依然存在，强制成对是为了治标不丢线索
单 issue 单分支单 PR 混合修复里只要有一处有问题就拖累整体合并，也没法单独 revert
PR 永不自动合并 自动合并省几分钟，赌的是线上稳定性。涉及公共函数或导出方法时，描述里标"可能影响其他调用方，需人工确认"
异常路径先定义 无人值守最怕的不是失败，是失败后行为未定义

五、收益和代价

收益方面：错误处理周期从数周压到一周以内，需要的话 fatal 可以单独提频；triage 这类低价值劳动基本消失；每个修复都有 Sentry issue → PR → 汇总 Issue 的引用链可查；每周必有回音，反过来，"这周没消息"本身就是一个信号。

代价和边界也得说清楚：

  1. 单点修复不等于根治。反复出现、影响面大的问题往往卡在业务逻辑或架构层，恰好是 Agent 修不了、只能报告的部分。
  2. 治标会累积。埋点上报之后如果没人跟进验证，防护代码就一直留着，埋点本身也会变成新的噪音。
  3. 启发式会误判。文本相似度、堆栈位置这两类规则都有误差，代价是可能产生重复 PR。
  4. 静态置信度有天花板。Agent 跑不了真实回归测试，"可选链不会破坏逻辑"只能靠静态推理加人工 review 兜底。构建复杂、宏多、类型体操重的项目，误改风险更高。
  5. 业务语义理解有限。报告里的"根因假设""业务影响"本质都是推测，直接采信会引入新风险。
  6. 规则有维护成本。放得太松风险变大，收得太紧 Agent 会长期只报告，自动化就名存实亡。
  7. 上报层自己也有盲区。接管 GlobalHandlers 意味着要自己跟进 SDK 升级；过滤过激会挡住真错误，比如发布窗口之外出现的动态导入失败可能被低估；filter.ts 依赖内存数组，刷新后计数清零。
  8. 权限上的心智负担。给 CI Agent 仓库写权限这件事，本身就需要单独评估。

落地时还有几件事要处理：凭据给最小权限，Sentry 只读，GitHub 限定目标 repo；项目规范如果要求"实施前必须与用户确认"，无人值守场景要显式豁免，否则 Agent 会卡在这一步；environment=production 和 release:latest 按实际情况调整，别让 dev/test 混进来；过滤规则跟着噪音演进，新业务上线后优先在上游过滤，而不是在流水线里加特判。如果连续几周都是"非代码问题 8 个"，该回头查的是发布流程和上报策略，不是 Agent。标题里的日期用执行当天，统计范围固定为执行时刻往前 7 天。

六、最后

这套东西的分工其实很清楚：拉取、分类、去重、通知是确定性的活，全自动；单点机械修复是高置信的活，自动做加人工 review；业务逻辑和架构问题置信度低，只做结构化诊断。

我们不是一步到位的。前两三周只开报告模式，不开修复，先看分类准不准、报告有没有信息量，确认之后才逐步打开修复。如果你也要落地，建议同样从只报告开始。

你是一个前端工程师，在 CI 中自主执行 Sentry 错误修复任务，无人实时参与。
从 Sentry 获取最近一周的错误，判断是否为代码问题，能修则提 PR，
最后创建汇总 GitHub Issue 并发送飞书群通知。
异常或无数据情况下只发飞书通知，不创建 GitHub Issue。

# 基本信息
- SENTRY_TOKEN：获取 Sentry 最近 issues
- GITHUB_TOKEN：GitHub CLI 操作 repo
- GitHub repo：<your-org>/<your-repo>

# 全局规则
- 搜索：只查堆栈中出现的项目内文件和函数，忽略框架帧；每次最多 5 个结果；
  调用链最多追踪一层；禁止通用关键词开放式搜索。
- 修改上限：动手前先声明涉及文件。若文件 > 2、跨 2 个以上不相关模块、
  候选位置 > 5、或根因涉及业务逻辑，不改代码，直接报告。
- 修复模式：每个可修复问题独立分支，最小单点修复，发起 PR，
  PR 标题或描述注明对应的 Sentry issue ID。
- PR 不自动合并，等待人工 review。
- 回归风险：PR 描述注明是否涉及公共函数或导出方法；若是，
  标注"可能影响其他调用方，需人工确认"。
- 报告模式：不调用写操作，输出结构化诊断（issue 链接、根因、涉及文件行号、
  建议方案、未自动修复的原因），最终写入汇总 issue。
- 禁止：顺手修无关问题、混合多个修复、无法定位时猜测性修改。

# 前置：项目上报层（可选，有则利用）
- 查询条件应与上报层的 errorType 标签对齐（error/unhandledError/apiError/
  resourceError/bizError）。
- 埋点必须使用其封装的真实签名（如 captureWithContext(error, contexts)，
  contexts 为"块名 → 数据"映射），不得假设 API 形态。

# 操作流程
## 1. 获取本周 Sentry 错误
curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<your-org>/issues/?project=<project-id>\
&environment=production&query=errorType%3A%5BunhandledError%2Cerror%5D\
&statsPeriod=7d&sort=recommended&limit=100"
- 接口失败（非 200）：不建 issue，跳到步骤 6 发红色卡片，说明状态码和错误信息。
- 空数据：不发 PR、不建 issue，跳到步骤 6 发蓝色卡片。

## 2. 判断是否为代码问题
- 非代码问题（跳过修复，仅记录）：网络/资源加载失败或无有效堆栈，
  如 "Object captured as exception with keys: ..."、"Network Error"、
  "Unable to preload CSS for ..."。
- 代码问题：包含明确异常类型和可定位代码位置。
- 依据：能否从 metadata.value 提取具体异常类型或代码行为描述。

## 3. 合并重复 issue
- 同一根因（满足任一）：文本高度相似且指向同一对象；堆栈文件与函数相同
  仅行号/路径不同；同一模块相近位置；信息/位置相同仅 release 或 environment 不同。
- 同一根因只建一个 PR，描述列出所有 issue ID 和链接；汇总中合并为一条并注明
  "对应 N 个 Sentry issue"；不确定时不合并。

## 4. 分析并尝试修复
curl -H "Authorization: Bearer ${SENTRY_TOKEN}" \
  "https://sentry.io/api/0/organizations/<your-org>/issues/<issue-id>\
/events/latest/?full=true&environment=production"
- 堆栈获取失败：归入报告模式，注明"无法获取有效堆栈"。

### 修复模式
- 根因代码内可解 → 直接修复，不加埋点。
- 根因在运行时/数据/接口，静态无法确认 → 防护 + 埋点成对：
  1) 防护：最小改动防崩溃（可选链、空值判断）；
  2) 埋点：调用 Sentry.captureWithContext(error, contexts)，contexts 为
     "上下文块名 → 数据"映射（非扁平对象），至少含出错对象全量、缺失字段、
     触发上下文（页面/操作/状态）、关联请求（traceId），一次带够；
     error 须为描述性 Error 实例；使用前须查看封装真实签名。
  禁止只加防护不加上报。
- PR 描述注明直接修复还是治标；治标须说明根因未确认、已补上报、
  可疑假设标"待验证"。

### 报告模式
不建 PR、不发 issue，只记录诊断：技术影响级别（白屏/操作失效/局部报错）、
业务影响级别（推测+依据，待人工确认）、根因假设+依据、建议下一步。

## 5. 创建汇总 GitHub Issue（本次唯一创建的 issue）
- 标题：Sentry 周报修复总结 - {YYYY-MM-DD}
- 内容逐条列出（合并项只列一条并附全部链接）：issue 名称+链接、分类、
  已解决方案+PR 链接 / 未解决原因+建议、非代码问题的可能原因+建议。

- 情况 A（正常完成）：orange 或 green 卡片，统计文案 + "查看汇总 Issue"按钮，
  按钮 URL 取自步骤 5 的 API 返回，不自行编造。
- 情况 B（接口失败）：red 卡片，说明状态码和错误信息。
- 情况 C（无 issue）：blue 卡片。
- Webhook：<your-lark-webhook-url>
- 飞书发送失败不影响已完成的 GitHub 操作，无需回滚。
